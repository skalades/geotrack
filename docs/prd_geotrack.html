01 Latar Belakang & Tujuan
GeoTrack Cikelet PRD v2.0

1.Latar Belakang & Tujuan

Dokumen ini adalah versi revisi dan peningkatan dari PRD v1.0. Berisi spesifikasi lengkap sistem GeoTrack Cikelet mencakup seluruh fitur fungsional, non-fungsional, arsitektur teknis, skema database, API specification, dan roadmap pengembangan.

1.1 Latar Belakang Proyek

Proyek pengukuran 200 titik GCP/ICP (Ground Control Point / Independent Check Point) menggunakan metode GNSS Statis di wilayah Cikelet, Garut Selatan menghadapi tantangan utama berupa:

🌳
Halangan Tajuk Pohon

Risiko data Float akibat canopy ekstrem yang mengganggu sinyal GNSS, memerlukan validasi visual kondisi langit di lapangan.

📡
Area Blank Spot

Wilayah Cikelet pedalaman rentan kehilangan sinyal internet, mengharuskan kemampuan kerja offline pada aplikasi lapangan.

👥
Koordinasi Tim

Sinkronisasi antara Project Manager, tim surveyor lapangan, dan klien membutuhkan platform terpusat dan real-time.

📋
Dokumentasi QC

Standar Quality Control membutuhkan dokumentasi foto dari 4 mata arah angin di setiap titik pengukuran.

1.2 Tujuan & Sasaran Sistem

  • Memantau progres harian 200 titik pengukuran secara real-time dan dinamis dengan dashboard visual interaktif.
  • Menyediakan wadah dokumentasi visual titik pengukuran dari 4 mata arah angin dengan validasi metadata EXIF otomatis untuk keperluan Quality Control (QC).
  • Menerapkan Role-Based Access Control (RBAC) dengan 3 level pengguna yang memiliki hak akses berbeda sesuai peran kerja.
  • Mendukung operasi offline (PWA) untuk surveyor di area tanpa sinyal dengan sinkronisasi otomatis saat ada koneksi.
  • Meminimalkan risiko kecurangan data melalui validasi EXIF koordinat GPS dan timestamp pada setiap foto yang diupload.
  • Menyediakan tampilan peta interaktif untuk visualisasi distribusi dan status 200 titik GCP/ICP secara spasial.
  • Menyediakan sistem ekspor laporan dalam format PDF, Excel/CSV, dan file RINEX untuk kebutuhan klien dan manajemen.

1.3 Scope & Batasan

✅ Dalam Scope

  • Web Application (desktop) untuk PM & Admin
  • Progressive Web App (mobile) untuk Surveyor
  • Dashboard monitoring & analitik
  • Form input data lapangan
  • Upload foto 4 arah + RINEX file
  • Validasi & persetujuan PM
  • Tampilan peta (Map View)
  • Sistem notifikasi in-app
  • Export PDF/Excel/CSV/RINEX
  • Audit log & riwayat aktivitas

❌ Di Luar Scope (v1.0)

  • Pemrosesan data GNSS / post-processing
  • Integrasi dengan software survei (Trimble, Leica)
  • Analisis akurasi koordinat otomatis
  • Mobile native app (Android/iOS)
  • Integrasi dengan sistem GIS enterprise
  • Billing / invoice management
  • Multi-proyek dalam satu instance

3.4 Spesifikasi Form Input Lapangan (Mobile-First)

Form dirancang responsif & mobile-first untuk kemudahan akses surveyor via smartphone langsung di lokasi patok atau premark. Mengutamakan tap targets besar, input minimal, dan auto-fill data.

📋 Bagian A — Metadata Titik

  • Kode Titik: Dropdown dinamis dari DB target (GCP-001 s/d ICP-200)
  • Tipe Titik: Auto-fill dari kode (GCP / ICP)
  • Operator Rover: Auto-fill dari akun login surveyor
  • Tanggal Pengukuran: Auto-fill hari ini, bisa diubah
  • Waktu Mulai Sesi: Input manual atau tap "Mulai Sekarang"
  • Waktu Selesai Sesi: Input manual atau tap "Selesai"

📡 Bagian B — Kondisi Teknis

  • Tinggi Antena: Numerik presisi 3 desimal (misal: 1.732 m)
  • Kondisi Sekitar: Pilih satu: Terbuka / Tajuk Ringan / Tajuk Rapat
  • Cuaca: Pilih: Cerah / Berawan / Hujan
  • Merk & Tipe Receiver: Dropdown atau input manual
  • Catatan Tambahan: Textarea opsional untuk keterangan lapangan

📁 Bagian C — Upload Dokumentasi

  • File RINEX: Upload file hasil observasi statis (.zip, .obs, .nav, maks. 50 MB)
  • 4 Foto Mata Angin: Wajib semua diisi sebelum submit (lihat detail di Seksi 3.5)
⚠️
Aturan Validasi Submit
Form tidak dapat dikirim (submit) ke server sebelum: (1) keempat foto mata arah angin berhasil diupload, (2) file RINEX/koordinat dasar berhasil diunggah, dan (3) semua field mandatory (bintang merah) terisi lengkap.

3.6 Alur Detail Validasi & Proses Retake

Alur Approve (PM)

  1. PM lihat daftar "Under Review"
  2. Buka detail: cek foto, EXIF, data teknis
  3. Jika valid → klik "Approve"
  4. Status berubah ke "Approved"
  5. Surveyor & Client mendapat notifikasi
  6. Data terkunci, tidak bisa diedit lagi

Alur Retake (PM)

  1. PM lihat daftar "Under Review"
  2. Buka detail, temukan masalah data
  3. Isi form alasan retake (wajib)
  4. Klik "Minta Retake"
  5. Status kembali ke "In Progress"
  6. Surveyor mendapat notifikasi + alasan PM
  7. Foto lama disimpan sebagai histori retake
  8. Counter retake bertambah (+1), maks 3x

3.7 Tampilan Peta Interaktif (GIS Map View)

Peta interaktif menggunakan Leaflet.js + OpenStreetMap untuk visualisasi distribusi spasial dan status 200 titik GCP/ICP di wilayah Cikelet, Garut Selatan.

Fitur Peta

  • Pin warna berdasarkan status titik (abu = unassigned, kuning = progress, biru = review, hijau = approved, merah = retake)
  • Klik pin → popup detail: kode titik, surveyor, status, foto thumbnail
  • Zoom in/out dan drag navigasi peta
  • Filter layer berdasarkan status, surveyor, atau tanggal
  • Tampilkan batas area proyek (polygon)
  • Toggle satelit / OpenStreetMap basemap

Kontrol Peta

  • Search titik berdasarkan kode
  • Cluster pin otomatis saat zoom jauh
  • Ekspor tampilan peta sebagai gambar PNG
  • Surveyor: lihat posisi GPS diri sendiri di peta
  • Jarak dari posisi ke titik target (navigasi)
  • Offline tile caching untuk area proyek

3.10 Audit Log & Riwayat Aktivitas

Setiap aksi penting dalam sistem dicatat otomatis untuk keperluan akuntabilitas, debugging, dan dispute resolution:

Event yang Dicatat

  • Login / Logout (dengan IP & device info)
  • Create / Edit / Delete master titik
  • Assign / reassign titik ke surveyor
  • Submit form pengukuran
  • Approve / Retake oleh PM
  • Upload file (foto & RINEX)
  • Download/Ekspor data
  • Create / Edit / Deactivate user

Data yang Tersimpan per Log

  • Timestamp — Waktu kejadian (UTC+7)
  • User ID & Role — Siapa yang melakukan
  • Action — Jenis aksi dilakukan
  • Entity & ID — Data yang terdampak
  • Old Value → New Value — Perubahan status
  • IP Address — Dari mana aksi dilakukan
  • Notes — Catatan tambahan (untuk retake)

5.2 Offline Capability (PWA)

📶
Strategi Offline-First untuk Surveyor
Aplikasi wajib berfungsi penuh tanpa koneksi internet untuk fitur-fitur kritikal surveyor. Data tersimpan di IndexedDB/localStorage dan disinkronkan secara antrian (FIFO queue) saat koneksi kembali tersedia.

Fitur yang Berjalan Offline

  • Lihat daftar titik yang di-assign (cached)
  • Buka dan isi form input pengukuran
  • Ambil foto & simpan lokal
  • Simpan draft form ke IndexedDB
  • Lihat peta offline (tile ter-cache)

Perilaku Sinkronisasi

  • Auto-sync saat koneksi terdeteksi
  • Upload antrian (queue) FIFO
  • Conflict resolution: server menang
  • Notifikasi "Data berhasil disinkronkan"
  • Badge jumlah data offline di UI

5.3 Kompresi Gambar Otomatis

  • Foto dikompresi di sisi client (browser) sebelum upload menggunakan Canvas API atau library browser-image-compression
  • Target ukuran: maksimal 1.5 MB per foto
  • EXIF metadata (GPS koordinat, timestamp) dipertahankan setelah kompresi
  • Resolusi minimum yang dapat diterima: 1280×960 piksel
  • Format output: JPEG (quality: 85%) atau WebP (quality: 80%)

5.4 Ketersediaan & Reliabilitas

  • Uptime target: 99.5% per bulan
  • Backup database: Harian otomatis, retensi 30 hari
  • Backup file: Foto & RINEX backup ke cloud storage
  • Recovery Time Objective (RTO): < 4 jam
  • Maintenance window: Minggu, pukul 00:00–04:00 WIB
  • Graceful degradation: Jika server down, PWA masih bisa digunakan offline
  • Health check: Monitoring endpoint setiap 5 menit

09 Keamanan (Security Requirements)

9.Keamanan (Security Requirements)

9.1 Autentikasi & Otorisasi

AreaImplementasi
Password HashingBcrypt dengan salt rounds minimal 12
Token ManagementJWT dengan secret key HS256/RS256, rotasi refresh token
RBAC EnforcementMiddleware validasi role di setiap endpoint sensitif
Brute Force ProtectionRate limiting 5 percobaan login / 15 menit per IP
Account LockoutAuto-lock 30 menit setelah 10 gagal login berturut-turut

9.2 Keamanan Data & Transport

AreaImplementasi
HTTPSWajib SSL/TLS di semua endpoint, redirect HTTP → HTTPS
CORS PolicyWhitelist domain yang diizinkan, reject origin asing
Input ValidationSanitasi & validasi semua input server-side (express-validator)
SQL Injection PreventionPrisma ORM parameterized queries (tidak ada raw SQL)
XSS PreventionContent Security Policy headers, DOMPurify di frontend
File Upload SecurityValidasi MIME type, scan virus (optional), batas ukuran file
Storage SecurityFile disimpan dengan nama acak (UUID), bukan nama asli
Environment VariablesSemua secret key di .env, tidak di-commit ke repository

9.3 Validasi Integritas Data Lapangan

🛡️
Anti-Kecurangan Data (Data Integrity)
Sistem harus mempersulit manipulasi data lapangan. Foto yang diupload harus langsung dari kamera, bukan screenshot atau gambar dari galeri lama.
  • EXIF GPS Check: Foto tanpa metadata GPS koordinat ditandai sebagai peringatan merah ke PM
  • Geofence Validation: Koordinat EXIF foto harus dalam radius 500m dari titik target terdaftar
  • Timestamp Validation: Timestamp EXIF foto harus dalam rentang waktu sesi pengukuran (±2 jam)
  • Hash Verification: Checksum MD5/SHA256 file RINEX dicatat saat upload untuk verifikasi integritas
  • Audit Trail: Setiap upload foto/RINEX mencatat IP, device, dan timestamp di activity log

9.4 Keamanan PWA (Mobile)

  • IndexedDB ter-encrypt menggunakan Web Crypto API untuk data sensitif yang di-cache offline
  • Service Worker hanya berjalan di HTTPS origin yang valid
  • Auto-clear cache IndexedDB saat logout pengguna
  • Token JWT tidak disimpan di localStorage (gunakan httpOnly Cookie atau memory)
